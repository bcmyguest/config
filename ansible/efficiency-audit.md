# Efficiency audit — 3 confirmed issue(s)

## 1. Serial GitHub API calls on every role — High — FIXED (3d72f9d, github-release-cached role)
**Where:** `roles/*/tasks/main.yml` (19 roles call `community.general.github_release`)
**Issue:** Every role in the provisioning playbooks makes a serial HTTP request to GitHub's API (`GET /repos/{owner}/{repo}/releases/latest`) on every run to check for a new upstream version. With 19 roles across both playbooks (nvim.yml + ai-inference.yml), this is 19 serial API calls that dominate the provisioning time. The GitHub API module returns `changed: false` when the local binary is current, but the network round-trip always happens regardless of whether a release was published.
**Cost:** ~75-115s total runtime overhead. Each role's `github_release` call takes 3-6s on a typical network. 19 roles x ~4s average = ~76s. This is the biggest contributor to the total playbook runtime and is purely serial — no caching, no conditional gating on `--tags` (the module runs whenever the role is reached).
**Fix:** Replace per-role `github_release` calls with a single `set_fact` of known versions at the top of the playbook (or in vars), and skip the HTTP call entirely when running with tags (e.g., `when: ansible_run_tags is not defined or 'version_check' in ansible_run_tags`). Alternatively, cache the last-seen release tag in a file and skip if unchanged. For `--tags` runs this eliminates 0s of overhead; for full runs it trades 19 serial API calls for 0 (or 1 cached lookup).

## 2. Ghostty AppImage forced download every run — Medium-High — FIXED (temp download + atomic copy)
**Where:** `roles/ghostty/tasks/main.yml:68` — `get_url` with `force: true`
**Issue:** The ghostty role does a proper version comparison (`target_version != current_version`) before entering the install block, but `get_url` uses `force: true`, which unconditionally downloads the entire AppImage (175MB+) every run, discards it, and then runs `set_fact` and `debug` that all say the version is already current. The download happens in the block guarded by the version check, but the real problem is that even when the version *does* change, the AppImage is downloaded to `~/.local/bin/ghostty` directly (the install path), bypassing download-then-verify. On a re-run with the same binary (e.g., network glitch, interrupted run), the next provisioning run re-downloads it again from scratch.
**Cost:** ~175MB network transfer and 15-40s per re-run, wasted when: run is interrupted mid-download, local AppImage is corrupted, or running with `--check`-adjacent workflows. On a full run (first time) this is unavoidable; on a re-run that hits the install block, it's a full re-download even though the version comparison already confirmed a change. The bigger issue: `force: true` combined with `dest: ~/.local/bin/ghostty` means the binary is downloaded and overwritten in-place — if the download is interrupted, the installation is broken and the next run re-downloads. Should download to a temp path and move only on success, matching the strategy used in `mise`/`nvim`/`uv` roles.
**Fix:** Download the AppImage to a temp file first, verify, then atomically move it into `~/.local/bin/ghostty` (removing the old one). Drop `force: true` and use the `creates` parameter so ansible skips the task if a valid binary exists.

## 3. python-debian pip install with no idempotency guard — Medium
**Where:** `roles/packages/tasks/debian.yml:8-11`
**Issue:** The `ansible.builtin.pip` task for `python-debian` runs unconditionally on every Debian/Ubuntu run — no `when` guard, no `register` + `when` pattern, no `state: latest` idempotency. The pip module does check installed packages, but on a pipx-installed Ansible (venv-first), the check involves launching pip, querying the environment, writing to stderr, and always marking `changed: true` when it touches the venv. The module itself returns `install_summary` but the task lacks a `changed_when` to suppress the change notification when the package is already present. Combined with the `deb822_repository` that follows, a failed pip install breaks the entire subsequent repo setup on a single machine — not a scaling issue per se, but a reliability fragility that costs a full re-run on any network hiccup.
**Cost:** Adds 3-8s to every provisioning run on Debian/Ubuntu (pip venv check + download time even if package is present). The task always runs regardless of whether `python-debian` is installed. With the deb822 repos and the legacy source cleanup shell command that follows, a failed pip install cascades into the entire packages role failing on a single-box provisioning run.
**Fix:** Guard with a pre-check (`stat` for the pip module or import check) and `changed_when` to suppress the always-true change notification. Or better: ship `python-debian` as part of the Ansible venv setup (outside this role) so this task doesn't need to run at provisioning time.

## Clean paths (not findings)
- Role serial ordering in `nvim.yml` is intentional (e.g., `cargo` before `mise` before `claude-code`) and correct.
- `import_tasks` with `when` guards in the packages role correctly limits OS-family work to one branch.
- Most other roles use `unarchive`/`copy` with idempotency checks (checksum-based diff), so they only download when truly needed.
- The `starship-claude` settings.json slurp-merge pattern is idempotent (JSON diff prevents writes when unchanged).

_*This is a focused top-3 audit on runtime, network, and reliability hot paths in a provisioning playbook — not an exhaustive coverage review._*
